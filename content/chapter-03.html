3.1 显存还有空位，为什么接不进请求？

把 GPU 显存想成酒店。如果一个旅行团必须住连续房间，即使各楼层总共有 9 间空房，也可能找不到连续 7 间。这是传统连续分配的外部碎片类比，不代表所有现代 GPU 分配器的实际行为。

另一种浪费是先给每个请求预留最大长度，实际输出很短却长期占着大段空位。分页分配则把空间切成固定容量的块，按需增加；最后一个块中尚未使用的位置属于内部碎片。

模型权重、激活和运行时工作区也占显存。显卡总显存不能全部算作 KV 预算。分页提高空间利用率，不会让显存变成无限。

3.2 KV Block：逻辑连续，物理分散

PagedAttention 将 KV 组织成固定 Token 容量的块，并让注意力 Kernel 按块映射读取它们。它借鉴虚拟内存的思想，在推理引擎内部实现管理，不是要求操作系统替 GPU 自动换页。

设 Block Size S = 16。40 个已处理 Token 需要 ceil(40 / 16) = 3 个逻辑块，分配 48 个位置，尾部空 8 个。Block Table 可以把逻辑块 0、1、2 分别映射到物理块 7、2、11。

块数 = ⌈T / S⌉
逻辑块索引 = ⌊i / S⌋，块内偏移 = i mod S

i 从 0 开始计数。第 20 个 Token 对应 i = 19：逻辑块 1 → 物理块 2，块内偏移 3。Kernel 根据这些地址读取 K/V，再完成同样的注意力数学运算。

3.3 Allocate → Append → Free

  1. Allocate：请求获准运行后，从可用块池分配本轮所需块，并建立映射。
  2. Append：每处理一个新位置，写入对应层的 K/V。块满后再申请新块。
  3. Free：请求结束后释放它的引用；不再使用的块可以回收。
  4. Retain / Evict：可复用前缀可能暂留，空间紧张时按策略淘汰。

例如已缓存 30 个 Token 时占 2 块；再处理 2 个位置后刚好填满；处理第 33 个位置时才需要第 3 块。这里计数的是已完成模型前向计算的位置，不是刚采样、尚未回送的 Token。

小块降低尾部浪费，但块数、元数据与访问管理开销增大；大块更易管理，但尾部浪费和复用粒度更粗。对单个未共享序列，单组固定块的尾部浪费小于 S 个位置。

3.4 Prefix Cache：相同开头，只算一遍

多个请求使用相同系统提示词与文档前缀，可以复用已计算的前缀 KV。后续各自的问题仍需单独计算，并读取公共前缀。这可以减少重复 Prefill，也可以减少公共 KV 的重复存储。

  • 必须是兼容模型、权重或适配器、Token 序列、位置等条件下的相同前缀；多模态输入还要包含相应输入身份。
  • 相似语义、相同词句出现在不同历史之后，都不足以保证 KV 相同。
  • 缓存必须已计算且仍然可用。常见实现按完整块命中，部分尾块与最后位置可能需要重算。
  • 它主要节省 Prefill 工作，后续 Decode 仍要做自己的生成计算，也仍需访问历史 KV。

共享块通过引用计数管理，A 结束不代表 B 正在使用的块可被覆盖。引用数降为 0 后，块可能仍保留可复用数据，直到被重新分配或淘汰；共享的可写尾部若要修改，应进行写时复制或采用等效保护机制。

3.5 显存不足时，系统有哪些选择？

方式用什么换空间代价
等待 / 限制接入减少驻留请求排队延迟上升
抢占与重算释放部分请求的 KV，后续恢复计算重复 Prefill 与时延波动
KV Offloading转移到其他存储层传输、同步与恢复开销
KV 量化减少每元素字节数精度、缩放元数据与 Kernel 支持的权衡

这些是设计选项，并非每个引擎版本都支持或默认开启。权重量化与 KV 量化是两回事：权重变小不会自动让 BF16 KV 也变小。

3.6 调度与缓存：两张预算表一起看

Scheduler 决定处理谁、处理多少位置；Block Manager 确认能否放下并给出映射；Attention Kernel 沿着映射读取历史。计算预算足够但 KV 块不足，仍然不能随意接纳新请求。

PagedAttention 主要改变 KV 的组织与访问方式，提高显存使用效率和共享能力；它不改变完整注意力需要关注哪些历史位置。Continuous Batching 是调度方式，两者互相配合，但不是同一个技术，也不是唯一可能的组合。

设真正可用的 KV 池为 20 GiB，上例每块为 5 MiB，池内约有 4,096 块。每个 10,000 Token 请求需要 625 块，不考虑共享和额外预留时最多容纳 floor(4096 / 625) = 6 个。这只是固定长度下的存储上限，后续生成还会增长，实际可服务并发还受时延、算力和带宽限制。

复习卡片

块解决分配，表解决寻址，引用解决共享，调度把计算与显存预算连接起来。
40 个 Token，16 个一块，为什么不是只分配 40 个位置？

块是固定容量单位，需要向上取整为 3 块，分配 48 个位置，尾部空 8 个。

两个请求的问题相同，就可以共享全部 KV 吗？

不能。还要看此前的完整前缀、模型和位置等条件是否一致，以及缓存是否仍在。

请求完成后，所有 KV 必须立即清零吗？

不必。解除引用后可按策略保留前缀数据；真正重新分配前须确保不会覆盖仍被引用的块。

术语速查

Logical / Physical Block
序列中的逻辑块 / 缓存池中的实际存储块。
Block Table
每个序列的逻辑块到物理块映射。
Reference Count
当前使用某个共享块的引用数量。
Eviction
淘汰可回收的缓存内容，让空间服务其他数据。
Copy-on-Write
共享内容发生写入时先取得私有副本，保护其他使用者。
